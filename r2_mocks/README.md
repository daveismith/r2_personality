# r2_mocks

Stand-ins for hardware the personality stack talks to, so the phase 1 slice runs and is tested
without it. Today: `dome_mock`, the dome device's LED and Magic Panel ROS surface
(`astromech_msgs` 2.0.0), and `dome_drive_mock`, the dome motor (section below). Plan: `docs/personality-phase1-plan.md` in `r2_dev`, sections 2.1-2.5
(the facts), 5.4 (what the mock offers) and step 2.

| file | what |
|---|---|
| `r2_mocks/led_model.py` | the LED displays, surfaces, runs, holds and attribution. Pure, no ROS. |
| `r2_mocks/magic_model.py` | the Magic Panel: 58-sequence catalogue, runs, poll granularity, holds. Pure. |
| `r2_mocks/console.py` | the device's console vocabulary applied to both models. Pure. |
| `r2_mocks/picture.py` | the text picture and the RGB image. Pure (numpy). |
| `r2_mocks/dome_mock.py` | the node: services, state topics, console, picture, image. |
| `config/dome_mock.yaml` | the catalogue, generated by `tools/gen_dome_mock_yaml.py` from the captures in `r2_personality/docs/dome/`. |
| `launch/dome_mock.launch.py` | `use_sim_time`, `config`, `state_hz`, `node_name`. |
| `r2_mocks/dome_plant.py` | the dome's motor: dead band, lag, coast, wrapped position with the firmware's crossing artefact. Pure. |
| `r2_mocks/dome_drive_mock.py` | the node: `/dome_controller/commands` in, `~/joint_states` (and `~/odom`) out. |
| `launch/dome_drive_mock.launch.py` | `node_name`, `use_sim_time`, `ideal`, `firmware_quirks`, `initial_rad`, `state_hz`, `publish_30hz`, `body_speed_m_s`. |

## Running it

The mock is a node named `r2_dome` by default, and every service and state topic hangs off the
node name (`~/leds/run` is `/r2_dome/leds/run`). **If the real dome is on the graph, rename the
mock**, or the two answer the same service names:

```bash
ros2 launch r2_mocks dome_mock.launch.py node_name:=dome_mock          # /dome_mock/leds/...
ros2 launch r2_mocks dome_mock.launch.py use_sim_time:=true state_hz:=10
ros2 run r2_mocks dome_mock --ros-args -r __node:=dome_mock -p state_hz:=5.0
```

The device's absolute topics (`/dome/text/line0`, `/dome/text/line1`, `/dome/audio/level`)
are used only by a mock named `r2_dome`. Under any other node name the mock listens on
`/<node_name>/dome/text/line0` and so on (a mock named `dome_mock` on
`/dome_mock/dome/text/line0`), so a real dome's topics are never touched. Tests run the node
with a unique name.

Manual check:

```bash
ros2 service call /dome_mock/leds/run astromech_msgs/srv/RunLedEffect \
  "{surface: fld, effect: fire, owner: me, priority: 10}"
ros2 topic echo /dome_mock/leds/states
ros2 topic echo /dome_mock/mock/picture
```

Foxglove: a Raw Messages panel on `/<node>/mock/picture` and an Image panel on
`/<node>/mock/image`.

## What it models, and how faithfully

The behaviour is the one in plan 2.3-2.5, which was read from the firmware (r2_domeplayer
445fdab and its 2.0.0 commits f843d69, 92b31f3) and **verified on the workbench dome on
2026-10-20**: attribution, the 5 s holds, the `priority` refusals in the device's order, the
text-slot rule, and the Magic Panel start/replace/stop behaviour against the Pico simulator.
Every rule has a test in `test/` that names it and quotes the refusal string.

LEDs (`led_model.py`):

- Runs replace across overlapping displays (`fld` overlaps `tfld` and `bfld`), `last_end:
  replaced` on the old run's surface; stop is exact; `all` is `rpsi`, `rld`, `fld`, `fpsi`, and
  is accepted only if every surface accepts (the ones that did keep their runs).
- Durations; self-ending `wipe`, non-looping clips (`failure` 18 s, `march` 48.3 s), text with
  `left`/`right`/`up`; `lightsout` holds; `cycle` reports `cycle:<child>` and changes every 10 s.
- Ending (any reason) restores each display's mode and picture; `last_end`, `last_effect`,
  `last_source`, `last_owner` stay across a new run.
- Configure: `APPLY_MODE` releases a run (`last_end: released`), brightness applies through a
  run, `MODE_SOLID` with `rgb` 0 keeps the colour, drift on a PSI named alone is `display has no
  drift` and skipped under `all`, a refused request changes nothing, `APPLY_SAVE` is accepted and
  never persists.
- Attribution: `source`, `owner`, `last_source`, `last_owner`, `changed_by`, `changed_by_owner`.
  A `console`, `ui` or `text_topic` write holds every display it touched for `hold_ms` (5000),
  renewed by each write. A ROS request at priority 1..199 touching a held display is refused
  `held by console`, `held by ui`, `held by text topic` or `held: manual`, checked after
  `owner too long`, `not fitted` and `unknown surface` and before anything applies. Priority 0
  and 200+ are never refused; ROS writes never hold and never end a hold.
- `leds owner manual` (hold everything, `HOLD_FOREVER`, `LedStateArray.manual`, the panel too)
  until `leds owner auto`, which also drops timed holds. `leds enable off` only darkens the
  strip: `strip_enabled` goes false and requests are still accepted and tracked, as the firmware
  does (it answers `not fitted` only when no strip is wired: the `fitted` parameter,
  default true, `-p fitted:=false`, which also takes the panel away).
- Text slots: a new message on `/dome/text/line0|1` starts `say fld` with both slots (bounce,
  linked, over the drift, no duration); both empty stops a `text` run on `fld`. Either is a
  `text_topic` write. `leds rostext off` makes the slots inert.
- Audio level stored and reported (`level`, `level_set`); no effect.
- A name over 96 bytes or a text line over 128 gets no reply from the device: the mock logs a
  WARN, sleeps `too_long_sleep_s` (5.5, past the 5 s client timeout) and then replies
  `request string too long` having applied nothing.

Magic Panel (`magic_model.py`): the 58 v012.1 sequences with names; `start` replaces, moves
`run_counter` by one (wraps at 256) and confirms; `unknown sequence`, `out of range` (`end`
above 1, `mode` above 1), `not supported by this panel` (`repeat` other than 1 without
`has_repeat`), `not fitted`, `firmware too old`; timed sequences end by `length_ms` (state
COMPLETE), loops and the random shows (56, 57) run until stopped, the random shows alternate a
10 s pattern with a 60 s dark pause (`in_pause`, `sub_seq` 254); stop blank/freeze gives
STOPPED and keeps the attribution; `started_by`, `owner`, `ours`, `takeovers`, `source`,
`sequence_id`, `remaining_known`/`remaining_ms`; the panel hold (`held_by`, `hold_remaining_ms`,
`manual`) for starts and stops at priority 1..199. State advances only on the 1 s poll, so the
state topic lags a start by up to a second while the reply carries the counter at once.
`ConfigureMagicPanel` takes no priority and is not gated by the hold, as on the device.

## The console path

Publish `std_msgs/String` lines on `~/mock/console` to play the operator at the dome. A line is
applied as the firmware would: attributed `console`, never refused for a hold, holding what it
touched. A leading `ui` attributes the write to the touchscreen (`ui leds run ...` or
`ui run ...`). Unknown lines and refused ones log a WARN.

```
leds run <surface|all> <effect|clip> [-c rrggbb] [-s 1-9] [-t seconds]
leds say <surface> [-m bounce|loop|left|right|up] [-k] [-b] [-c rrggbb] [-s n] [-t s] <top>[|<bottom>]
leds stop <surface|all>
leds mode <display|all> random|solid|off|text|manual
leds fill <display|all> <rrggbb>        leds text <display|all> <text>
leds brightness <display|all> <n>       leds drift <display|all> calm|lively
leds enable on|off    leds owner manual|auto    leds rostext on|off    leds level <0-255>
magic_panel start <id|name> [-r repeat] [-e blank|leave]
magic_panel stop [blank|freeze]         magic_panel fit on|off
rotary <0-9>                            a GPIO run: source 3, started_by other, takeovers +1
```

`-k` links the two lines, `-b` puts the text on black. Flags come after the surface (or
sequence) word and before the text.

## Gate order

A ROS request is checked in this order, and the first failure is the reason (the device's own
order for the part the plan fixes; the first two are the mock's choice):

1. `owner too long` (32 bytes or more)
2. `not fitted` (LEDs: no strip wired, `fitted` false; panel: link absent, with `firmware too old` ahead of
   it for an unsupported panel)
3. `unknown surface` (configure: `unknown display`, the mock's wording, not captured from the
   device; run/say/stop say `unknown surface` as the device does)
4. the hold: `held by console|ui|text topic` or `held: manual`, only at priority 1..199, over
   all the displays the request touches, before anything applies (so `all` is all-or-nothing)
5. the request's own checks (effect or clip, `no clip for this surface`, text rules, ranges)

For the panel, step 3 is the sequence check (`unknown sequence`, then `out of range`, then
`not supported by this panel`) and follows the hold.

## Threads

Services run in a reentrant callback group on a 4-thread executor, with one lock around the
models, so the deliberate no-reply wait (`too_long_sleep_s`) does not stop the state topics.
The wait ends early on shutdown.

## Knobs

Parameters, read at startup: `config` (catalogue YAML, default the installed one), `state_hz`
(1, up to 10), `hold_ms` (5000), `fitted` (true: a strip and a panel are fitted, one flag for both models), `too_long_sleep_s`
(5.5), `use_sim_time`. A droid's own `ListLeds`/`ListMagicPanel` capture replaces the
catalogue: `python3 tools/gen_dome_mock_yaml.py LEDS.txt MAGIC.txt > config/dome_mock.yaml`.
To test a panel without `CAP_REPEAT`, copy the YAML, set `has_repeat: false` under
`magic.panel` in the copy (the generated file is not edited in place) and pass it as `config`.

## Known gaps

- A request that touches several surfaces (`all`) is all-or-nothing on a hold; the firmware
  goes surface by surface and joins the refusals as `<surface>: <reason>; `. Single-surface
  requests, which is all the arbiters send, are identical.
- No pixel-accurate effects: the image shows mode and effect colour only, no animation.
- No clip pull (`leds pull`); the clips are the catalogue's, as captured.
- No servos (phase 0's `servo_sim` covers the dome servos), no `/dome/joint_*`, `/dome/buttons/*`.
- No WiFi faults, no 1.2-1.5 s outliers, no inbound-burst wedge; round trips are about 1 ms
  (`magic/start` blocks 10 ms, as the device does up to 30 ms).
- Self-ending durations of `wipe` (100 ms a column at speed 5) and of `left`/`right`/`up` text
  (120 ms a column at speed 5, 6 columns a character) are approximations of the firmware's.
- The text speed, the solid colour of a `text`/`manual` display and `leds level` effects
  (`micbright` and friends do not follow the level) are not modelled; `leds scroll` is absent.
- `cycle` picks its children from `rainbow`, `roam`, `fire`.
- Rotary position n starts sequence n (the real mapping is the panel's); `stop` blank and freeze
  give the same STOPPED state (the panel's picture is not modelled).
- Reply shapes: the models return tuples (LED) and dicts (panel), not one `Result` type; the
  node's `_serve` helper hides the difference.
- Only sequences flagged both LOOPS and RANDOM (the random shows, 56 and 57) have patterns and
  dark pauses.
- `unknown display` (configure with a display that does not exist) is the mock's wording; the
  captures do not include it.
- The state topic stamps with the node clock, not UTC.

## dome_drive_mock

The dome's drive for development without the robot or Gazebo (phase 2 plan 2.1, 2.3 and 5.5).
It subscribes `/dome_controller/commands` (`std_msgs/Float64MultiArray`, `data[0]` rad/s) and
**holds the last command** (the forward controller does; the converter's final 0 is what stops
the dome). `DomePlant` runs at 30 Hz on the node clock and the node publishes `~/joint_states`
(`dome_joint`, position only) at `state_hz` (10), `~/joint_states_30hz` with
`publish_30hz:=true`, and `~/odom` (`nav_msgs/Odometry`, 10 Hz, `linear.x` =
`body_speed_m_s`) only when `body_speed_m_s` is above 0. It does not run the converter: start
the real `dome_twist_converter` from `r2_bringup`.

```bash
ros2 launch r2_mocks dome_drive_mock.launch.py                  # /dome_drive_mock/joint_states
ros2 launch r2_mocks dome_drive_mock.launch.py ideal:=true      # like Gazebo
ros2 run r2_mocks dome_drive_mock --ros-args -r __node:=dome_drive_mock_t1 -p initial_rad:=1.0
```

Parameters, read at startup: `ideal` (false), `firmware_quirks` (true), `initial_rad` (0.0),
`state_hz` (10, up to 30), `publish_30hz` (false), `body_speed_m_s` (0.0), `use_sim_time`.
The commands topic is absolute; remap it (`-r /dome_controller/commands:=/x/commands`) to keep
a test off a real graph.

The plant (`DomePlant(ideal, firmware_quirks, initial_rad).step(command, dt)` returns the
reported position; `position_rad`, `velocity_rad_s`, `wrapped_rad`, `reported_rad`, `coasting`):

- dead band: `|v| < 0.44 rad/s` turns the motor off;
- lag: first order, 90 % of the commanded speed at 1.5 s (`tau` = 1.5 / ln 10);
- coast: when the motor goes off, a further `0.37 s * v - 4 deg` (never negative), slowing at a
  constant rate over exactly that distance;
- position wrapped to [0, 2*pi); with `firmware_quirks` the angle never reads inside
  (355 deg, 4 deg), so each crossing of 0, in either direction, is one 9 deg step between a
  355 deg and a 4 deg reading (the reading is a function of the true angle alone, error at
  most 4.5 deg, no drift);
- `ideal`: a pure integrator, the velocity is the command at once; the position is still wrapped.

The node tests start the real converter (`ros2 run r2_bringup dome_twist_converter`); they skip
if `r2_bringup` is not installed, because `r2_bringup` exec_depends on this package and a
`test_depend` back would be a cycle.

### Known gaps

- No `:DPA` position moves, no `~/set_home_here` or `~/setup`, no plausibility gate.
- No `DomeTelemetry` on `/roamadome/telemetry`; no velocity in the joint state.
- The lag is first order, not the measured step response; the coast is the linear fit
  `0.37 v - 4 deg`, not the real curve (the fit is reliable from about 2 rad/s).
- Positive and negative commands are symmetric (the real `velocity_map` differs per direction),
  and the motor driver's `min_percent` steps are not modelled.
- The crossing artefact is the 355 to 4 deg model above, not the firmware's exact quantisation.
- `~/joint_states` is stamped with the node clock, and nothing models a stalled or absent
  controller (the last command is held for ever).
